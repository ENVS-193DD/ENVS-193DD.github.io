Why are we using Git/GitHub?

Git and GitHub allow us to do a few important things in data science:

  • keep track of different versions of our work (so that old work is never lost forever)
  • store our work remotely (so that if our computers die, we still have access to our stuff)
  • reuse other people’s work (so that we can reproduce their work and also repurpose for our own needs)
  • collaborate with others (so that you’re not emailing, texting, etc. code back and forth)

See Horst and Lowndes, “GitHub for supporting, reusing, contributing, and failing safely.” for a broad overview of how Git/GitHub work together, and Jenny Brian’s “Excuse me, do you have a moment to talk about version control? for more.

What is the difference between Git and GitHub?

Git is what tracks your changes (and allows you to have version control), while GitHub is a cloud hosting service for those changes. We use both together.

Operations

Get familiar with these terms
  • repo: short for “repository”, think of this as a folder
  • remote: your repository on GitHub (in the cloud)
  • clone: essentially making a local copy (i.e. a copy on your computer) of a remote repo
  • commit: track the changes you’ve made using Git (on your computer only)
  • push: push the changes you’ve committed to GitHub (now in the cloud)
  • pull: pull changes from GitHub to your computer
  • fork: create a copy of someone else’s repo on GitHub
  • merge: incorporate remote changes into your local, or incorporate your local changes to the remote

Creating a repository and using Git/GitHub

1. Create a repository.

Go to the GitHub homepage.

Click the green “New” button.

2. Fill information about your new repository.

This includes the name, a description, whether it is public or private (keep your repository public for now).

Additionally, initialize your repository with a README. It is very important to start your remote repository with a file, and GitHub does it for you by creating a file called README.md.

A README file describes what is in the whole repository (code, data, etc). See the README resource for more details about what it is, but for now remember to always initialize your repository with a README.

3. Clone your repo to your computer.

When you are “cloning”, you are essentially making a local copy (i.e. on your computer) of your remote.

Do this by clicking the green “Code” button and copying the url that shows up.

Then, create a new project in RStudio.

Select “Version Control”.

Then, select “Git”.

Paste the clone url into the first box.

Keep your cursor in that box, then hit the Tab key. The new project directory name should automatically fill in.

Directory names

It is very important that your remote and local repositories have the same name. The easiest way to ensure this is by not typing anything into the second box. Paste the url into the first box, then hit Tab.

Then, select the folder on your computer where you are keeping all your repositories for Git/GitHub. If you created a folder called “Git” or “GitHub” in your root directory, use that folder. This is something that you only have to do once; for each subsequent repo you clone from GitHub, the file path will be automatically filled in.

After you have created your repository, a new RStudio window will open.

Verify that the clone has worked by seeing that you have:

  • a project (should be the same as the directory name)
  • the “Git” tab
  • a .gitignore file (a file that tells git which files to ignore when tracking changes)

4. Make changes to your repository.

Create a new Quarto document.

Type in some code.

Save your document.

Open up the Git tab in the top right. You should see your new .qmd file along with any other new files (the .gitignore and the .Rproj file.).

5. Commit your changes.

In the Status column, you will see two yellow question marks. This means that the files are new, and git isn’t tracking them yet.

Check the boxes next to each file, which turns the two yellow question marks to a green “A” for “added”.

Click “Commit”. A new screen will pop up that looks like this:

If you click through each file in the top left pane, you will see the changes to the file in the lower pane.

The top right pane is where your commit message goes.

Commit messages accompany each git commit and push. They should describe the changes to the file since the last version. They’re best as short phrases describing the changes. For a first commit/push, you could just write something like “initial commit”, as in the example.

Write a commit message, then hit “Commit”.

You should see a window that shows your commit message and a summary of the file changes.

Congratulations! Your files are now being tracked by git.

6. Push your changes.

Your file is now being tracked, but it’s not on GitHub yet.

To get your files on GitHub, push the commit. To do this, click the “Push” button. You should see a window that looks like this:

Double check that your push to GitHub by looking back at your remote. Refresh the repository page.

You should see your new files in the repository, and your commit message showing up next to the files that you changed.

Congratulations! Your files are now on GitHub.

7. Make more changes.

Version control only works if you actually use it. That means you should commit and push with each change you make. The frequency of committing/pushing you do depends on you. Some people are totally commit-happy and commit/push with every chunk of code they write; you might find it more reasonable to commit/push after each coding session.

Every time you make a change, your modified file will show up in the “Git” tab with a blue M for “modified”. The process for changes is the same as for new files:

  • Click the check box,
  • hit “Commit”,
  • fill in a commit message,
  • commit,
  • then push.

In the commit window, you’ll see any modified files with changes highlighted in green, as before.

Forking

Forking is the process by which you can copy and reuse another person’s code. Imagine having a meal with someone else, and using your fork to take something from the other person’s plate. You can then do whatever you want with the food you’ve taken: eat it, mix it with other things, etc. This is the idea behind forking.

1. Navigate to the repository you want to fork.

You should see a button to “Fork” in the top right.

2. Create the fork

Click “Fork”. You’ll be led to a screen to “Create a new fork”.

You can rename the repo if you want, or write a new description. You’ll also copy the main branch.

You will have to wait for a bit.

Once it’s done, you should see a screen that looks like a normal repo with some indications that you have forked someone else’s repo:

  • under the repo name, you will see “forked from” another repo.
  • a message saying “This branch is up to date with…”

3. Clone the repo.

This is the same process as cloning your own repo.

Click the green “Code” button and copy the url that shows up.

Then, create a new project in RStudio.

Select “Version Control”.

Paste the url you copied and hit tab.

Make sure that you are creating a project as a subdirectory of your git/github folder.

4. Work in the repo.

This is the same as working in your own repo: write code, make changes, commit and push them.

Your changes will only be saved to your forked repo, not to the original repo. Thus, you are reusing people’s code and writing new code without overwriting their work.

Browsing your remote repo

GitHub allows you to easily browse the history of your repository. Think of this as time travel!

1. Find your commit history

Each commit/push you make to your repo gets stored in your commit history. The commit history is a list of all the commits you’ve made.

Find your commit history in your repo. It should look like an arrow in a circle with the number of commits you’ve made. Click this.

2. Browse your commit history

You can see the list of all commits you’ve made.

To see the details of a particular commit, click on the commit message.

This will lead you to a screen that displays the old verson on the left and what was added in that particular commit on the right.

3. Browse your repository

Back in the commit history, you have the option to browse your repository at the time of that commit (!!!).

If you click the <> button, it will take you back to the repository at the time of that commit. You can navigate the same way you would in a regular repository.

The url with the long code at the end indicates that you are browsing an old version of your repo.

GitHub for failing safely

The time travel aspect of GitHub is one of the best reasons to use GitHub. If you are committing/pushing your changes regularly, you will have each version of your repository saved in the cloud. These versions are all easily browsable. If you’ve deleted something and you decide you want it back, then you can go back and get it. Nothing is gone forever, and that’s a good thing when you’re changing your code, working with others, and adding more to your work.

Collaboration

Another powerful way to use GitHub is to work with other people. You can add collaborators to a repository and they can commit/push changes just like you can, and you can pull each others changes to your respective computers.

Successfully working together = frequent communication

GitHub is a powerful tool to collaborate, but it doesn’t replace good communication with collaborators. When working with someone else in the same repo, be sure to communicate with each other about what you’re doing, what part of the document you’re going to be working in, etc. This requires you to actually reach out and contact them - so do it!

Starting to collaborate

1. Add collaborators to your repo.

In your GitHub repo, navigate to Settings > Collaborators.

Find your collaborator by searching for their GitHub username.

Select their username.

Hit the green “Add … to this repository” button.

If successful, you should see the other person listed as a collaborator and a blue banner that says “… has been added as a collaborator on this repository.”.

Some in-class edits

It’s not actually important for a .Rproj file to be tracked by git or on the remote, so you can add it to the .gitignore, which is a file that tells git what not to track.

In class, the repo creator will modify the .gitignore file and stage/commit/push that change before the collaborator clones the repo to their computer.

2. For the collaborators

You will receive an email with an invitation to the repo. Accept the invitation.

You should then see something like “you have push access to this repository”. That means you can work out of this repo and commit/push changes as though it was your own.

Clone this repo to your computer.

Pulling changes

You and your collaborator will be working out of the same repo. That means that you can pull each others’ changes to your respective computers.

When collaborating with others, it is best practice to pull often. If you’re starting up a coding session, pull any changes. Before you push changes, pull more changes.

Pull changes by hitting “Pull” in the Git tab.

A window should pop up with a summary of changes, additions, deletions, etc. that you are pulling from the remote.

You will then see the changes on your computer!

Order of operations

After you make a change, the order of operations should always be as follows:

1. Stage your change.

The pop up window should look the same as usual.

2. Commit your change.

Write a commit message…

Then hit Commit.

3. Pull any potential changes.

It is very important to pull prior to pushing your change. This ensures that any changes your collaborator made are present in your local repo.

Ideally, if you have been pulling regularly, you will see a message that says something like “Already up-to-date.”

4. Push your change.

Same as always.

5. Tell your collaborators that you just pushed changes so that they can pull those changes.

For the collaborator, pull those changes.

Again, it is good practice to pull often.

Remembering the order of operations

The RStudio IDE shows you the steps in the order in which they are supposed to occur.

Remember:

  1. Stage.
  2. Commit.
  3. Pull.
  4. Push.
  5. Tell your collaborators!

Following this order of operations prevents situations called “merge conflicts” which can range from easily fixable to extremely frustrating. See a guide to navigating merge conflicts here.

One easy way to avoid merge conflicts is to make sure that you and your collaborator are working on different parts of the document, or on different documents entirely. Once you’re both done with your respective parts, incorporate everything into one document.

Dealing with merge conflicts

Sometimes things go awry when you’re collaborating. If you haven’t communicated that you’re committing/pushing changes and your collaborator makes changes without pulling yours, you will encounter a merge conflict.

What a merge conflict looks like

Let’s say you have already staged (step 1) and committed your change (step 2).

When you pull (step 3), you will see a message that looks like this:

Oh no! This is a merge conflict.

First, stay calm! Then, follow the directions as the error gives you.

Run git merge --no-ff in the Terminal.

This forces your change and the change on the remote to come together into a merge conflict.

Identifying a merge conflict

What you should see is something like this in your script:

The <<<<<<< HEAD and >>>>>>> refs/remotes/origin/main are the start and end of the section of code with the merge conflict. This is the section that you and your collaborator were trying to edit at the same time.

The ======= separates your change (above) and the other person’s change (below).

It is now your responsibility to resolve this conflict!

Edit the script as necessary

You might decide to delete text, replace it, etc.

Whatever you do, communicate with your collaborator about what you are doing.

Once you resolve the conflict, you can stage and commit your change as usual.

Pull prior to committing.

Then push!

Getting changes into your forked repository

Sometimes you will have forked a repository and made your own changes to files. Once there is a change in the original (“upstream”) repository, you may want to incorporate those changes into your own fork without losing your changes.

Source credit

Thanks to Clark Richards for a very informative blog post explaining this process.

Verifying that there have been changes to the repository

When you have made a change and the “upstream” has made a change, your remote fork will show you something like this:

Some number of commits “behind” means that there have been changes to the original repo that you do not have in your fork.

Check your connection to remote repositories.

In RStudio, navigate to the Terminal.

To check connections to remote repos, type:

git remote -v

You should see an output that shows “push” (where you push changes to) and “fetch” (where you get changes from).

Set the upstream repo.

In this step, you have to tell git which repository is the “upstream” repository from your fork.

Find the git url for the original repository by visiting the page for the original repo and copying the url from the green “Code” button.

Back in the RStudio terminal, type git remote add upstream, add a space, and paste the URL. Your command should look like:

git remote add upstream https://github.com/REPO-OWNER/REPO-NAME.git

Hit enter/return.

Double check that you have correctly added the upstream repo by running:

git remote -v

You should now see the upstream repo in the output.

Fetch changes from the upstream

Get the new changes from the upstream repository by running:

git fetch upstream

git is now understanding that there are new changes from the upstream repo.

Merge changes from the upstream

To incorporate changes from the upstream repo, run:

git merge upstream/main

Note: When you run this command, you will see different outputs in the Terminal prompting you to write a commit message. What you see depends on your operating system, so don’t panic if you see something different.

Toggle to see the two options.

  • Option 1: Vim
  • Option 2: Pico

You may see something like this:

You can edit the commit message (at the top of the output: “Merge remote-tracking branch upstream/main”), or you can leave as is.

Hit Ctrl + C. Once you do so, you should see a message at the bottom that states: Type :qa and press <Enter> to exit Vim.

Type :qa and press Enter/Return.

You should then be led back to what looks like a normal Terminal window.

Then, PUSH those changes.

You may see something like this:

You can edit the commit message (at the top of the output: “Merge remote-tracking branch upstream/main”), or you can leave as is.

Hit Ctrl + X.

You should then be led back to what looks like a normal Terminal window.

Then, PUSH those changes.

You have successfully incorporated changes from the upstream repo and pushed those changes to your own fork.

Looking at the commit history

On your own commit history, you will be able to see the commits from the upstream repo describing the change and your own commit from merging those changes into your repository.

### Pulling changes

You and your collaborator will be working out of the same repo. That means that you can **pull** each others' changes to your respective computers.  

When collaborating with others, it is best practice to **pull** often. If you're starting up a coding session, pull any changes. Before you push changes, pull more changes.  

Pull changes by hitting "Pull" in the Git tab.

![](/resources/images/github/51_rstudio-pull.png){width=80%}

A window should pop up with a summary of changes, additions, deletions, etc. that you are pulling from the remote.  

![](/resources/images/github/52_pull-window.png){width=80%}

You will then see the changes on your computer!

![](/resources/images/github/53_new-changes-on-computer.png){width=80%}

**Remember:**

1. Stage.
2. Commit.
3. Pull.
4. Push.
5. Tell your collaborators!

Following this order of operations prevents situations called **"merge conflicts"** which can range from easily fixable to extremely frustrating. See a guide to navigating merge conflicts [here](https://learning.nceas.ucsb.edu/2023-04-coreR/session_10.html#merge-conflicts).  

One easy way to avoid merge conflicts is to make sure that you and your collaborator are working on different parts of the document, or on different documents entirely. Once you're both done with your respective parts, incorporate everything into one document.

### Dealing with merge conflicts

Sometimes things go awry when you're collaborating. If you haven't communicated that you're committing/pushing changes and your collaborator makes changes without pulling yours, you will encounter a **merge conflict**.

#### What a merge conflict looks like

Let's say you have already staged (step 1) and committed your change (step 2).  

When you pull (step 3), you will see a message that looks like this:


![](/resources/images/github/62_conflict.png){width=80%}


Oh no! This is a **merge conflict.**

First, stay calm! Then, follow the directions as the error gives you.

#### Run `git merge --no-ff` in the Terminal.

This forces your change and the change on the remote to come together into a **merge conflict**.

![](/resources/images/github/63_merge.png){width=80%}

#### Identifying a merge conflict

What you should see is something like this in your script:


![](/resources/images/github/64_identifying-conflict.png){width=80%}


The `<<<<<<< HEAD` and `>>>>>>> refs/remotes/origin/main` are the start and end of the section of code with the merge conflict. This is the section that you and your collaborator were trying to edit at the same time.

The `=======` separates your change (above) and the other person's change (below).

It is now your responsibility to resolve this conflict!

#### Edit the script as necessary

You might decide to delete text, replace it, etc.

Whatever you do, **communicate with your collaborator about what you are doing**.

![](/resources/images/github/65_resolving.png){width=80%}

Once you resolve the conflict, you can stage and commit your change as usual.

![](/resources/images/github/66_commit.png){width=80%}

Pull prior to committing.

![](/resources/images/github/67_pull.png){width=80%}

Then push!

![](/resources/images/github/68_push.png){width=80%}

## Getting changes into your forked repository

Sometimes you will have forked a repository and made your own changes to files. Once there is a change in the original ("upstream") repository, you may want to incorporate those changes into your own fork without losing your changes.

:::{.callout-note title="Source credit" collapse="true"}
Thanks to Clark Richards for a very [informative blog post](https://www.clarkrichards.org/2021/11/28/forking-and-syncing-branches-with-git-and-github/) explaining this process.
:::

### Verifying that there have been changes to the repository

When you have made a change and the "upstream" has made a change, your remote fork will show you something like this:

![](/resources/images/github/upstream-changes/02_remote-diff.png){width=80%}

Some number of commits "behind" means that there have been changes to the original repo that you do not have in your fork.

### Check your connection to remote repositories.

In RStudio, navigate to the Terminal.

To check connections to remote repos, type:

```bash
git remote -v
```

You should see an output that shows "push" (where you push changes to) and "fetch" (where you get changes _from_).

![](/resources/images/github/upstream-changes/03_init-remote-v.png){width=80%}

### Set the upstream repo.

In this step, you have to tell git which repository is the "upstream" repository from your fork.

Find the git url for the _original_ repository by visiting the page for the original repo and copying the url from the green "Code" button.

Back in the RStudio terminal, type `git remote add upstream`, add a space, and paste the URL. Your command should look like:

```bash
git remote add upstream https://github.com/REPO-OWNER/REPO-NAME.git
```

Hit enter/return.

Double check that you have correctly added the upstream repo by running:

```bash
git remote -v
```

You should now see the upstream repo in the output.

![](/resources/images/github/upstream-changes/04_add-upstream.png){width=80%}

### Fetch changes from the upstream

Get the new changes from the upstream repository by running:

```bash
git fetch upstream
```

git is now understanding that there are new changes from the upstream repo.

![](/resources/images/github/upstream-changes/05_git-fetch-upstream.png){width=80%}

### Merge changes from the upstream

To incorporate changes from the upstream repo, run:

```bash
git merge upstream/main
```

![](/resources/images/github/upstream-changes/06_git-merge-upstream-main.png){width=80%}

**Note:** When you run this command, you will see different outputs in the Terminal prompting you to write a commit message. What you see depends on your operating system, so don't panic if you see something different.

Toggle to see the two options.

:::{.panel-tabset}
#### Option 1: Vim

You may see something like this:

![](/resources/images/github/upstream-changes/06a_vim.png){width=80%}

You can edit the commit message (at the top of the output: "Merge remote-tracking branch upstream/main"), or you can leave as is.

Hit `Ctrl` + `C`. Once you do so, you should see a message at the bottom that states: `Type :qa and press <Enter> to exit Vim`.

Type `:qa` and press Enter/Return.

You should then be led back to what looks like a normal Terminal window.

![](/resources/images/github/upstream-changes/06b_return-from-vim.png){width=80%}

Then, **PUSH** those changes.

#### Option 2: Pico

You may see something like this:

![](/resources/images/github/upstream-changes/06c_pico.png){width=80%}

You can edit the commit message (at the top of the output: "Merge remote-tracking branch upstream/main"), or you can leave as is.

Hit `Ctrl` + `X`.

You should then be led back to what looks like a normal Terminal window.

![](/resources/images/github/upstream-changes/06d_return-from-pico.png){width=80%}

Then, **PUSH** those changes.

:::

**You have successfully incorporated changes from the upstream repo and pushed those changes to your own fork.**

### Looking at the commit history

On your own commit history, you will be able to see the commits from the upstream repo describing the change and your own commit from merging those changes into your repository.


![](/resources/images/github/upstream-changes/07_commit-history.png){width=80%}
